# Method: portable genealogy-vault methodology

The reusable "how" of an autoresearch genealogy vault — conventions, the person
meta-block grammar, integrity rules, and operational style. This file is **vault-
agnostic**: nothing here names a real person, and it is meant to be reused
verbatim across vaults. It is tracked, and `CLAUDE.md` `@import`s it, so a clone
loads it automatically.

**The private half stays local.** Per-client facts — the subject, the
generation-anchor table, a given vault's lineage→file layout — are real family
data, so they live in a `CLAUDE.instance.md` that is gitignored. The convention
is a thin, also-gitignored `CLAUDE.local.md` that `@import`s your instance file;
create one if you want per-vault facts in context. Nothing in this file depends
on either existing. See CONTRIBUTING.md "The framework/private boundary".

## Project Structure

The generic dir roles (`prompts/`, `reference/`, `workflows/`, `vault-template/`) are in **CLAUDE.md** (loaded alongside this file). A working install adds:
- A **vault directory** — the live, populated working tree (Family_Tree files + data). `vault-template/` is the empty starter you copy from; the vault is the instance. Keep it as its own repo (or at least gitignored): it holds real people and must never be committed to the framework repo.
- **Per-vault instance constants live in the vault's `.autoresearch.json`, read via `scripts/vault_config.py` (zero-dependency JSON loader) — NOT hard-coded in the scripts** (extracted 06 JUL 2026 for multi-vault / contract reuse). Covers: the GEDCOM filename (`gedcom`; falls back to the single `*.ged`), and the "structurally unsourceable" rules (`structural_gap`: `deep_gen_threshold` + region-scoped rules) consumed by `harvest_sources.py` and `build_edges.py` — **prefer `before_year`, which states the CRITERION, over the `pid_prefixes`/`pids` enumerations, which drift** (operator ruling 05 AUG 2026, Q157/Q144: the reference vault's rule keyed on FS-PID prefixes, an opaque external key, and had fallen 16 entries short of the cluster it describes; an entry with NO dated vitals never satisfies a `before_year` rule). Also: `anchor` (`kind: individual|couple` + `people[]` = the Gen-1 set; empty `people` synthesizes one person from `subject`; read via `vault_config.get_anchor`), `repositories` (id → read/write auth + `write.visibility`, default FamilySearch-only, a write target ships `enabled:false` unless opted in; `get_repositories`), and `hosts` (source-host registry, `locator_kind: ark|url|id`; `get_hosts`). Also: `person_model` (`file` default | `narrative`) selects how person records are stored on disk — one Markdown file per person (upstream/legacy) vs many people per lineage file, each a bold-name entry with an inline `- meta:` block; read via `vault_config.get_person_model` (an unrecognized value is a hard error, not a silent fallback). **Omit a block to accept its default — do NOT copy the default `repositories`/`hosts` into a vault config just to have them; write only what deviates.** Shape reference: `vault-template/.autoresearch.example.json`. An absent file/key falls back to generic defaults, so a fresh vault runs with zero config. When adding a new per-family constant to a script, put it here behind the loader instead of inlining it. (`session_audit.sh` similarly externalizes its advisory baseline to the vault's `.audit_baseline.txt`.) **Which vault the toolkit operates on** is resolved centrally by `vault_config.resolve_vault()` — precedence `AUTORESEARCH_VAULT` env var → a script's `--vault` arg → (a `../vault` sibling **only if one exists**, else a clear error). **There is NO implicit default vault** — you must say which vault you mean, so one toolkit install drives many vaults: `AUTORESEARCH_VAULT=~/vaults/<name> python3 scripts/gen_person_index.py --integrity`. Export `AUTORESEARCH_VAULT` before launching so the SessionStart audit + pre-commit run against the right vault (the pre-commit auto-points at the vault it is committing). **ONE narrow exception, and only for the read-only SessionStart banner** (widened 29 JUL 2026): requiring the env var meant that forgetting to export it produced a session with no gate values, no census and no frontier count, and *no error to notice* — the failure the rule was meant to prevent traded for a silent one. So `session_audit.sh` resolves in four steps — env → `.claude/last_vault` (which it writes on every success) → the sole vault-looking dir in the project → **ask** — and **always names the source in the banner**, because a hook runs non-interactively and cannot confirm anything itself: an `env` resolution is an explicit choice, an inferred one must be confirmed by the agent before any write, and 2+ candidates are never guessed. Point it elsewhere with `bash scripts/session_audit.sh --set-vault /path/to/vault`. `resolve_vault()` itself — the path every MUTATING script takes — stays strict, because a labelled read is safe where a silent write is not. A new per-script `--vault` arg should be wired as `vault_config.resolve_vault(args.vault)`.

## Vault Template Conventions

The **generic** file-frontmatter conventions — the `type`/`created`/`tags` minimum, the person/transcription/region/surname frontmatter fields (incl. `life_status` / `evidence_tier` / `profile_status`), the underscore-filename rule, the wikilink convention, and the `reference/vault-file-manifest.md` core-file names — live in **CLAUDE.md**, which Claude loads alongside this file. They are deliberately NOT restated here, so they cannot drift. (An earlier copy in this file had gone stale at `confidence` vs upstream's `evidence_tier`/`profile_status`; deferring to CLAUDE.md is the fix.)

**Deltas** for a vault on the `narrative` person model (the model this file documents):
- **People are recorded as bold-name NARRATIVE entries with a `- meta:` block** inside `Family_Tree*.md` (see "Person entry meta block" below) — NOT as per-person files. The template is [vault-template/templates/person_narrative.md](vault-template/templates/person_narrative.md); the per-person YAML *file* ([vault-template/templates/person.md](vault-template/templates/person.md)) is the other supported model, and the framework default.
- **Region / surname content is inline** ("Origins and Toponymy" sections within the lineage file), not separate `type: region` / `type: surname` files. **Size exception:** when a lineage file crosses the shard threshold and the Origins prose is the growth, the essay moves to a `Family_Tree_<Region>_Origins.md` companion (a 2-line pointer stays inline in the lineage file).

## Style

The generic style rules (no hyphens-as-punctuation, no emojis, source-first, log negative results, confidence tiers Strong/Moderate/Speculative, living-person privacy) are in **CLAUDE.md**. This vault's additional operational rules:

- **The session loop is FOUR PHASE PROMPTS and two commands (mechanized 29 JUL 2026; split into phases 31 JUL 2026).** A session runs `21-session-start` (initialize: gate state vs baseline, vault confirmed, session number, Handoff read, operator items surfaced), then `22-research-iterations` (**the only loop**, `Iterations: N` lane draws), then `23-session-review` (reconcile against the tools, re-measure every lane metric, assemble the FS write-back queue), then `24-session-close` (file it). The two commands sit inside phases 2 and 4. `python3 scripts/session_plan.py` prints ONE ranked worklist across **THREE** lanes — EXPAND (parentless SILENT frontier), IMPROVE, ROTATE (the profile-review draw)

  - **⛔ VERIFY WAS COLLAPSED INTO IMPROVE, 02 AUG 2026 (operator; deferred 39 + 40). There are THREE lanes.** The two already drew from mostly the same people — **694 in both, 72% of IMPROVE and 71% of VERIFY-PID** — and the two jobs are ONE ACTION: `25-person-research-sweep` cannot harvest a person's FamilySearch sources without loading the profile, which *is* the liveness check. Stale-PID work had been justified as protection for IMPROVE's own harvest, i.e. it was a **precondition wearing a lane's clothes**.
  - **THE COLLAPSE IS ASYMMETRIC, AND THAT IS THE WHOLE DESIGN.** IMPROVE stood at 0 wins / 9 and VERIFY at 11 / 13, latterly on PID checks alone; a naive merge would hand the expensive lane a cheap way to meet a floor it had never met, so every honest miss would become a hit and the vault would stop seeing that six-source sweeps are slow. Therefore **confirming an FS PID is live SCORES NOTHING** — it is **step 0 of prompt 25**, annotated on drawn rows, never a unit.
  - **AND `?` STOPPED DEFINING A POOL (deferred 39).** Keying the lane on a mark the vault puts on ITSELF meant it saw **76 of 2,393 edge tokens (3.2%)**, never re-examined the other 96.8%, and could not see **any** of the 8 children carrying an unexplained PARENT-GEN MISMATCH — the vault's own strongest "this edge is wrong" signal, drawn by nothing. IMPROVE now carries a third population, **DEFECT** = gate findings + unadjudicated `?` edges, with a reserved share of every draw (`IMPROVE_DEFECT_SHARE`). `build_edges.gen_mismatches()` is the SHARED computation behind both the gate line and the worklist, so the banner and the lane cannot drift.
  - IMPROVE proper is SOURCE_GAP + SINGLE_SOURCED entries (**redefined 31 JUL 2026, deferred 24** — it was keystone LOAD×THIN, which measures whether an entry was WRITTEN UP rather than whether it is SOURCED, and the two populations measured disjoint; `keystone_report` remains as a report). Its dispositions are recorded split three ways: **`--sourced`** (0 records → cited), **`--corroborated`** (1 host → 2+), **`--verified`** (a DEFECT row settled). A draw that was all-defect is legitimate and is visible as such, instead of reading like a draw that achieved nothing.
  - Each lane is fed by the owning tool's own candidate-builder; `session_plan` draws the recommended one with a **bandit over lanes** (state in the vault's `session_plan_snapshots.json`; bootstrap floor, staleness floor, then exploit) and prints the **Lane target**. ⚠ **A lane whose DEFINITION changes must get a `lane_epochs` entry**, which retires its old observations from the floors while keeping them in `history` — IMPROVE got one on 02 AUG 2026 for exactly this reason, and the retired VERIFY arm moved to `retired_arms` rather than being deleted.
  - **⚠ CANDIDATES ROTATE; THE HEAD OF A LANE IS NO LONGER FIXED (operator-directed, 01 AUG 2026).** Three of the four lanes ranked candidates with a DETERMINISTIC sort and took the top N, so a row that was open but merely HARD sat at the head of its lane every session for ever: on the reference vault one parent edge was walked and classified a permanent FS-GAP in **three separate sittings**, by three sessions that each reached the same answer unaided, and it still ranked FIRST in the next draw. `adjudicated` (deferred 32) fixed only the SETTLED half of that. Two mechanisms now sit on top, both in `session_plan.py` and pinned by `scripts/test_candidate_rotation.py`: (a) a per-lane **cooldown** — a row offered and not disposed of goes to the BACK for `offer_cooldown` sittings (default 3, `.maintenance.json`); (b) a **seeded stratified sample** — the first `1/HEAD_FRACTION` of the target is still taken strictly by priority, the rest is sampled from the pool, seeded so the list is STABLE across the several plan runs inside one iteration and resamples for the next. **Cooldown, not randomisation, is what stops the repetition**: a shuffle makes repetition unpredictable rather than rare, and pure randomisation would discard the real priority gen-ascending encodes. **A cooled row is DEPRIORITISED, never removed** (the lane size stays honest, and if everything is cooling the plain order is returned). **Offers are stamped at `--record`, not at plan time** — the plan writes them to `pending.offered` and `record()` stamps them only when the recorded lane MATCHES the drawn one, so overriding the draw cools nothing, and the SessionStart hook's own plan run cannot cool rows nobody looked at. Keyed on the **vault `id`**, never an external PID — keying those two differently is exactly what broke the ROTATE cooldown on 30 JUL 2026.: a percent of the vault counted in PEOPLE, per ITERATION. **Each iteration records its own outcome** (`session_plan.py --record --lane <L> --outcome hit|miss`), where **hit = the lane target was met, or the lane ran dry; short of target is a MISS** (the older "the metric moved at all" produced sixteen straight hits, and an arm that never loses carries no signal). `python3 scripts/session_close.py [--log ... --summary ...] --next-plan` then runs the close checklist in order (plan outcome, rotation clock, Research_Log row, handoff lint, ascii, handoff archive, next draw) and reports every step rather than letting one be silently skipped; **it takes no `--lane/--outcome` by default**, because phase 2 already recorded each iteration and a second record double-counts one sitting. ⚠ **ORDER: record, THEN plan.** `--record` sets `pending: null`, so a `session_plan.py` run BEFORE the close is wiped by it — a Handoff announced a pending EXPAND draw over a state file holding none, and the next session drew a different lane. `--next-plan` runs it last so this cannot be got wrong (pinned by `scripts/test_session_close.py`). The SessionStart banner's `plan ->` line is state-only and cheap; the full plan is phase 2's first COMMAND, not hook work.
- **THE GOAL IS A COMPLETE BIOGRAPHY PER PERSON, AND FAMILYSEARCH IS ONLY THE SYNC POINT (operator, 01 AUG 2026).** *"The eventual goal is for every person in the vault to have as complete a biographical entry as possible. When we're researching an individual we should visit as many resources as possible to gather as many primary sources as possible... We shouldn't rely just on FamilySearch -- that's just the online place we've chosen to sync with."* Measured when this was written: **660 of the 691 entries citing any source cited FamilySearch, and only 26 people in the whole vault cited two or more hosts** -- and the IMPROVE lane was literally *defined* as "SOURCE_GAP entries with a harvestable FS PID", so a person with no FS profile could not enter the improvement lane at all. Four things now hold the goal in place, none of them an intention: (a) **`25-person-research-sweep`** is the default unit of research work -- FS Sources *and* Research Help hints *and* the discussions tab, then Ancestry, WikiTree and what it CITES, the region's own archive, newspapers/obituaries and the library surfaces, logging every resource including the empty ones; `19-fs-source-harvest` is now just its FamilySearch leg. (b) **IMPROVE is un-gated from `harvestable_pid()`** and each row prints a non-FS route hint for its region. (c) **`SINGLE_SOURCED` / `MULTI_SOURCED`** in the census heartbeat -- a CROSS-CUTTING count, deliberately not a category, because a person with 30 FS ARKs and nothing else is `WELL_SOURCED` and single-sourced at the same time. (d) **`bio_completeness.py`** measures whether a LIFE HAS BEEN WRITTEN (born/died/parents/spouse-or-children/sources as core; occupation/residence/migration/military/probate/narrative as enrichment) -- a different axis from the record census, and the one the goal is actually about. ⚠ Its LIFE facets are keyword-detected, so they are a FLOOR and never a total. **A record count is not a biography: thirty ARKs and no prose is not finished work.**
- ⭐⭐ **AND THE LINEAGE POINTS AT ITS OWN TRIED ROUTES — the `ROUTES ALREADY TRIED IN THIS LINEAGE` block at the head of every `Family_Tree*` file (operator-directed 03 AUG 2026).** *"In the entry for a person you should know what routes have already been tried — or at least the routes checked by others in the file."* Regenerate with `python3 scripts/route_digest.py --apply` (idempotent; report-only by default).
  - ⭐ **ROUTES ARE REGIONAL, NOT PERSONAL, which is why the per-person pointer does not catch them.** The worked failure: a session proposed an archive for a comune while working in one shard, and the measured answer — *that archive's holdings for that comune BEGIN in a stated year; do not re-run* — sat in a DIFFERENT PERSON'S entry in a SIBLING SHARD, recorded six weeks earlier. Two further route re-proposals in the same sitting had the identical shape.
  - **Scope is the LINEAGE** — a root file plus every file whose name extends it (`_Collateral`, `_Deep`, `_Origins`, …), derived from the filenames, which is the same boundary the content-routing policy splits on. ⚠ The bare `Family_Tree` stem is excluded from root candidacy: it prefixes every shard, and leaving it in collapsed the whole vault into ONE lineage (measured: 50 files, 184 statements, 1 group).
  - **CLOSED routes sort above OPEN ones**, because re-proposing a closed route is the expensive error and re-proposing an open one is harmless. Both are grouped **per shard** so the alphabetically-first file cannot eat the cap — which is exactly how the finding this tool exists for got truncated out of its own first draft.
  - ⚠ **THE BLOCK IS BLOCKQUOTED, AND THAT IS LOAD-BEARING.** A bold span at line start IS the person-entry grammar; an un-quoted digest would mint a phantom entry and silently steal the following lines from a real one (integrity rule 8, spec/entry-boundary). Every emitted line carries `> `.
  - ⚠ **Extract the WHOLE bullet, not one sentence.** The first draft cut at the first full stop and kept the alarm while dropping the fact — the boundary YEAR was in the second sentence. Verified to move **no census count** (0 of 1,382 rows) and to leave frontmatter, entry-boundary, META_PRESENCE and GEN_HEADING at baseline.
- ⭐⭐ **THE ENTRY POINTS AT ITS OWN PRIOR RESEARCH — read the `- **Prior work**` bullet FIRST (standing rule, operator-directed 03 AUG 2026).** Every person entry whose identifiers appear in `logs/` carries, immediately under its `- meta:` line, a bullet listing those sessions newest-first. **Read it before doing anything to that person.** Regenerate with `python3 scripts/log_backlinks.py --apply` (idempotent; report-only by default).
  - **WHY IT EXISTS, and the reason is a measured failure, not a nicety.** The dominant failure across ~20 sittings was **re-deriving work already done**. Session #137 lost two findings that way and wrote a bolded warning into `Handoff.md` — *"BEFORE RESEARCHING ANY QUESTION, GREP logs/"*. Session #138 **read that warning during phase 1 and then made the same mistake four more times**: it retracted a whole "conflation cluster" (Q142) that was four ordinary parent-named-on-a-child's-record attachments, and re-proposed three research routes this vault had already measured and closed. **The rule was delivered, read, and ineffective** — which is this vault's standing evidence that an un-mechanized rule drifts.
  - ⭐ **The mechanism is placement, not discipline.** A coverage ledger or a lookup script needs somebody to REMEMBER it; the entry does not, because it is impossible to work a person without opening it. **Put the pointer where the reader already is.**
  - **Measured at adoption:** 443 logs, **1,073 people identifiable in them, 101 entries linking any log, 995 entries with prior work and no pointer** (2,682 pairs). Worst: one ancestor with **19 prior sessions and no pointer**; another whose 30 attached sources were being audited in that very sitting had **12**.
  - ⚠ **Matched on IDENTIFIERS, never on names** — a log is credited only when it cites the person's vault `id` or an external id that resolves to exactly ONE entry. Name matching would attach the wrong [ANCESTOR] to the wrong entry in a village where three generations share a forename. A token claimed by two people is DROPPED, not guessed.
  - ⚠ **"This log discussed this identifier" is NOT "this log is about this person."** A log that considered and REJECTED a PID still cites it — and that rejection is precisely the prior work a later session must not redo.
  - ⚠ The bullet goes **directly under `- meta:`**, never above it (a bullet above makes the roster and `prose_audit` read the wrong display name). Verified at adoption to move **no census count**: 995 bullets, 0 of 1,382 CSV rows changed.
- Check before searching. Before researching an ancestor, grep `vault/logs/` and `vault/Open_Questions.md` for their name to see what has already been tried. Do not repeat prior negative searches unless using a new source or strategy. ⭐ **The `- **Prior work**` bullet above is the cheap version of this check and should be read first; the grep remains the thorough version, and is still required for a person the bullet does not cover (no identifier in any log) and for PLACES, REPOSITORIES and ROUTES, which the bullet does not index at all.**
- **Check FS source citations before launching gap-fill scans.** Before running repeated scans of archive registers (Antenati, FamilySearch image collections) for a known person, open that person's FamilySearch profile, click the **Sources** tab, toggle **Detail View** on, and check each source for a "**Web Page (Link to the Record)**" field. Community contributors often paste the direct Antenati ARK to the source image. That image may sit in an adjacent fascicolo (e.g., a matrimoni processetti bundle) containing additional documents (estratti, marriage atti, consent docs) that resolve the question in one drill. Worked example: one ancestor's death date was resolved by a single FS source-link trace after ~1,200 gap-fill register scans had already been run on the wrong hypothesis — check the citations first.
- **Downsize register images before reading them with the Read tool.** Files saved from FamilySearch (`3Q9M-*.jpg`), Antenati, Geneteka, etc. are typically 3000-4500 px wide. The Anthropic API auto-downsizes images to about 1.15 MP for the model but still transmits the full base64 payload, so a 4218×3007 page costs roughly 10× more request bytes than the model actually uses. Multiple Reads of one large image over a long session can push the total request past the 32 MB API ceiling (`request_too_large: 413`). Before Read, run `sips -Z 1500 input.jpg --out /tmp/input-small.jpg` and Read the small copy. **To read a *specific* atto/entry at full cursive detail, crop just that region instead of downsizing the whole page: `magick input.jpg -crop WxH+X+Y /tmp/atto.png` (offset is +X+Y from top-left; optionally add `-resize 180% -normalize -sharpen 0x1` to aid 19th-c cursive), then Read the small crop — full detail for the region of interest at low payload.** ImageMagick 7 is installed at `/opt/homebrew/bin/magick` (PIL/Pillow is NOT installed — use ImageMagick, not Python PIL). If full resolution is genuinely needed across a whole page or for interactive locating, use the localhost-HTTP + browser zoom path instead, which keeps the full-res image out of the conversation context entirely. Incident to avoid: a 4218×3007 jpg Read 10× over one long session pushed the payload past 32 MB and blocked all further prompts with 413 until the file was removed.
- **Declarant-age estimates are ESTIMATES, not facts.** When a vault row's birth year is derived from an Italian (or other) 19th-century atto declarant-age field ("age 47 in 1879" → b.~1832), mark it as an estimate and expect ±2-12 yr outlier from any FS-corroborated birth year. Multiple datapoints across 19th-c Italian collateral rows have shown a consistent ±2-12 yr range, weighted toward 8-12 yr for older collaterals. Always prefer FS-precise birth years over declarant-age-derived estimates when both exist. When matching a declarant-derived vault row against FS Family-tab siblings, expand the age-window match tolerance to ±12 years rather than the usual ±2.
- **Append to the Research_Log "## Session Index" via `scripts/log_session.py`, NEVER via the Edit tool.** The prompts say "append a one-line summary entry to the session index" but name no tool; an Edit forces a full Read of the ~35k-token append-only file just to add one row. Use `python3 scripts/log_session.py --log "logs/YYYY-MM-DD-slug" --summary "..."` (structure-aware: inserts at the bottom of the table, before any trailing section; appends by default, `--dry-run` to preview). This file is append-only — nothing should ever full-read it into context.
- **A person entry states CURRENT state; the sequence of how it was learned lives in `logs/` (rule added 29 JUL 2026).** The dominant failure mode in prose quality is append-only supersession: a dated bullet is added, a later bullet corrects or completes it, and BOTH remain — so an entry reads as 16 bullets of session history in which a superseded research plan still looks live ("This note stood for seven weeks reading as an open task after it had been completed within hours", as one entry's own retraction puts it; the worst file measured 6,700 tokens per person against a corpus median of ~500). The rule: when a bullet supersedes an earlier one, the superseded bullet MOVES to the session log that documents the work (or a dated supersession log), and the entry keeps one current-state bullet plus the log pointer. Dated bullets are for FACTS with dates (a record, a negative search), not for narrating the entry's own revision history. The same applies to hand-`~~strikethrough~~` inside entries: a struck claim with a `SUPERSEDED` continuation is history — move it to the log. (Deliberate discrepancy MARKERS on a bold name being tracked as a known same-name hazard are the exception, and should never sit at line start where they read as entry grammar.)
- **⭐ ANYTHING THAT NEEDS FURTHER RESEARCH TO RESOLVE GETS AN `Open_Questions.md` ENTRY, IN ADDITION TO THE NARRATIVE (standing order, operator-directed 02 AUG 2026).** The narrative bullet is not enough and never was. **A person entry states CURRENT STATE; `Open_Questions.md` is the register of what is UNRESOLVED** — so a discrepancy written only into an entry is invisible to every mechanism that picks work, and simply waits for someone to re-read that entry by chance.
  - **The evidence for the rule.** One sitting's harvests surfaced: **a Gen-9 ancestor's MATERNITY** — his father had two wives, the child's 1767 birth fell in range for both, and the answer decides an entire Gen-11 branch — walked and adjudicated two sessions earlier, written into the entry (correctly, with the `adjudicated:` key), and **never raised as a question**; three competing marriage dates for one couple; three vault-vs-record date conflicts; and three children left unnamed because their registrations index under the father. **Every one was in an entry and none was in the register**, and the maternity case had been sitting that way for weeks.
  - **The threshold — a question is owed when RESOLVING IT NEEDS WORK NOT YET DONE**: a source located but not read, a record not yet found, a choice between candidates, a contradiction between a vault value and a record. **NOT owed** for something you actually settled, and NOT for a closed negative with no remaining route — that is a **declaration** on the entry (and, if it should leave a worklist, a `structural_gap` rule).
  - **Batch the thin ones.** Several low-stakes findings of the same shape belong in ONE numbered question with a table, not three. Proliferating near-empty questions makes the register unreadable, which defeats it.
  - **Cross-link both ways**: the entry names the question (`tracked as [[Open_Questions]] Q114`), the question names the ids and the locators. The entry then keeps ONE current-state bullet, per the supersession rule above.
  - ⚠ **Say what would settle it.** A question without a named resolver — a specific record, register, or repository — is a complaint, not a research task.
- **Resolve an Open_Question with a PLAIN heading + terminal status; do NOT hand-strikethrough it.** When a question is fully resolved, change its heading to `### N. Title — RESOLVED <date> (note)` (terminal status — `RESOLVED` / `RULED OUT` / `CLOSED` / `CONFIRMED FAIL` / `FULLY RESOLVED` — must be the FIRST word *after the last em-dash*, so put any qualifier in parens AFTER it: `— RESOLVED 30 JUN 2026 (pirate detach)`, never `— pirate detach RESOLVED`). Leave the resolution write-up in the body. **Do NOT manually wrap the heading in `~~strikethrough~~`.** When the archiver migrates the block it now **removes the block entirely** and records ONE terse line in a single **`## Resolved & Closed — Index`** section (compact-index model adopted 01 JUL 2026, replacing the old per-question inline struck-heading tombstones — 0 wikilinks depended on the in-file anchors, and 45 scattered struck headings were more clutter than the breadcrumb was worth). A hand-struck heading still migrates fine (detection keys on terminal status, not the `~~`). To sweep resolved entries into `Open_Questions_Resolved.md` (when the file is over its `.maintenance.json` token threshold): `python3 scripts/archive_sections.py --target open-questions` (dry-run) then `--apply` (versioned snapshot to `Open_Questions_Archive/`, idempotent; full text -> Resolved file + one index row -> live file). One-time back-fill of legacy inline tombstones: `--migrate-tombstones` (done 01 JUL 2026: 48 converted).

## Person entry meta block (the machine-readable person record; v3 YAML-flow grammar adopted 24 JUN 2026)

**This section describes the `narrative` person model** (`person_model: narrative` in `.autoresearch.json`) — many people per lineage file, each a `- meta:` entry. The framework also supports the default **`file`** model (one `type: person` Markdown file per person, YAML frontmatter); the two encode the SAME `PersonRecord` fields and are inter-convertible (`scripts/convert_person_model.py`, runbook [workflows/switch-person-model.md](workflows/switch-person-model.md)). All record-consuming tooling reads/writes through the model-agnostic seam `scripts/person_store.py` (`iter_people`/`write_person`, dispatched by `vault_config.get_person_model`); the meta-block grammar below is how the narrative backend spells each field. See spec `optional-person-model`. The file-model spelling of the same fields is the person-file frontmatter (the optional `id`/`generation`/`parents`/`spouse`/`flags` keys added upstream), per the field-map at the end of this section.

The narratives are the single source of truth for people; **`Person_Index.md` was RETIRED and deleted on 24 JUN 2026**. Each person entry in a `Family_Tree*.md` file carries a **machine-readable meta block** as its **first body bullet**, directly under the bold-name header. The gen-sorted roster the old index provided is produced ON DEMAND: `python3 scripts/gen_person_index.py --write /tmp/roster.md`. See `scripts/gen_person_index.py` (generator / `--integrity` gate / `--gap-report`), `scripts/mint_ids.py` (id minter).

Copy-paste template: **[vault-template/templates/person_narrative.md](vault-template/templates/person_narrative.md)** (the narrative-entry + meta-block shape; [vault-template/templates/person.md](vault-template/templates/person.md) is the standalone per-person-file model).

**v3 grammar = a VALID YAML flow-mapping** (adopted to maximize compatibility with the upstream `templates/person.md` frontmatter vocabulary — see the field-map below). It is parseable by `yaml.safe_load` *and* by the zero-dependency reader in `gen_person_index._parse_flow_mapping` (PyYAML is optional). The format can't be file-frontmatter (that's per-file; the narrative model packs many people per file), but the inline flow-mapping is real YAML with upstream's exact field names + values.

```
**Jane Example Ancestor** (b. Dec 1840, Somewhereton; d. 1873; FS PID XXXX-XXX)
- meta: {id: P-7K3QM2, evidence_tier: strong_signal, profile_status: complete, life_status: deceased, generation: 6, fs: XXXX-XXX}
- **FS-attached sources** (...)
```

**The meta block — NOT the bold name — is the identity and detection anchor.** `gen_person_index` finds entries by their `- meta:` line and keys identity on `id`; it reads the bold name from the line above purely for DISPLAY + vitals. So a bold name with parens, quotes, commas, or lowercase words is fine — it can no longer make an entry invisible or duplicate it. Format the bold name for human readability; the machine never depends on it.

Grammar (YAML flow-mapping `{k: v, k: v}`; conventional field order below):
- `id` — the **vault-owned primary key**: `P-` + 6 Crockford base32 chars (no I/L/O/U), e.g. `P-7K3QM2`. **REQUIRED, unique, NEVER reused or hand-edited.** The ONLY identity key — dedup, matching, and Phase-2 `parents`/`spouse` edges reference `id`, never names/dates/external PIDs. Mint with `python3 scripts/mint_ids.py --apply` (idempotent; handles both grammars). A deleted entry's id is retired, not reused.
- `evidence_tier` — `strong_signal` / `moderate_signal` / `speculative` (upstream's claim-quality vocabulary). **OPTIONAL: absence = unassessed** (pair with `profile_status: stub`). There is NO `unknown`/`U` tier — "haven't assessed" is expressed by omitting the field, not by a fourth value.
- `profile_status` — `stub` / `partial` / `complete` (upstream's file-completeness vocabulary, **orthogonal to evidence_tier**: a well-sourced record can be `complete` with no `evidence_tier`, and a `strong_signal` claim can still be a `stub`). `complete` = the entry carries a **`- **Sources**` bullet**; `partial` = tiered but unsourced; `stub` = thin/unassessed collateral.
  - **AMENDED 23 JUL 2026 — a RECORD ARK is not the only thing that earns `complete`.** The old wording made `complete` mean "has an FS-attached-sources bullet", which silently tied a *documentation* judgement to one *evidence class*. For record-era ancestors that is harmless. For medieval, peerage and colonial-book lines it is simply wrong: those people are documented by charters, chronicles and scholarly compilations, and the Recipe-S policy **deliberately excludes** book/journal citations from the ARK metric (invariant 8, class (c)) so that coverage cannot inflate on bibliography. The two rules composed into an absurdity — a Carolingian cited to Cawley, Richardson and the *Monumenta Germaniae Historica* could never be better than `stub`, which reads as "nobody has researched this" about some of the best-documented people in the vault.
  - **The rule now:** `complete` is earned by a `- **Sources**` bullet citing EITHER (a) independent primary **records** (`host:locator` per Spec 03 — the ARK path), OR (b) **scholarly apparatus**: FMG Medlands (Cawley), Richardson *Royal Ancestry* / *Magna Carta Ancestry*, Complete Peerage, ODNB (with DOI), the Henry Project, MGH / named chronicles, Great Migration, NEHGR / TAG, published town Vital Records. Cite (b) with page or section refs in the bullet, the same way (a) cites locators. **This does NOT change the ARK coverage metric** — `harvest_sources` still counts only records, so the census stays honest. It changes only what the per-entry status field is allowed to claim.
  - **Not everything counts.** User trees (Geni, Ancestry, RootsFinder, copied WikiTree assertions) earn nothing under either limb — they copy each other, and often copy your vault. WikiTree's *cited sources* remain a separate corroboration layer, not a status upgrade.
  - **The matching census split:** `harvest_sources` now reports **`BOOK_SOURCED`** (0 ARKs, structurally unsourceable, but cites scholarly apparatus — finished work) and **`UNCITED`** (0 ARKs and no citation of any kind — the real worklist) in place of the single `STRUCTURAL_GAP`. At the split this vault's 186 structural entries were 101 / 85, so nearly half of what the census described as "cited in prose" was not cited anywhere. **`UNCITED` is the list to work, and its route is a library/archive pass, not an FS harvest.**
- `life_status` — `living` / `deceased` / `unknown` (upstream's privacy field). **Autonomous web research MUST skip `living` AND `unknown`.** For WRITE-BACK the gate is **per-target** (Spec 04, `multi-anchor-multi-repo`): a **public** target (a shared tree — FamilySearch, WikiTree) denies `living`/`unknown`; a **private** target (a personal Ancestry-style tree) may include them. This is decided in ONE place — `scripts/privacy_gate.py` `gate(vault, repo_id, life_status)` — which every write path calls (it also refuses a repo that is not a `write.enabled` target); do NOT restate the rule inline where it can drift. With no `repositories` configured the only target is public FS, so the effective rule is the historical "skip `living` and `unknown`". 110-year presumption seeds `life_status`; explicit "living"/"possibly living" in the header → `living`.
- `generation` — generation counted from the subject (Gen 1), integer, or omitted if undetermined. REQUIRED for the roster. Per-person source of truth (not inferred from `### Generation N` headings, which fail for theme-organized collateral). Phase 2: computed from the parent-edge graph.
  - **⚠ WRITE IT EXPLICITLY IN A `## Collateral stub entries` SECTION.** There is a fallback to the nearest preceding `### Generation N` heading, and it used to reach **across unrelated `##` sections** — a stub section has no Generation headings of its own, so the nearest one could sit ~180 lines and three sections above. An entry that deliberately omitted `generation` was silently relabelled **28 → 30** and duly reported as a Gen-30 frontier row; **no gate objected, because `NEEDS_META` is satisfied by a generation being FOUND, not by its being RIGHT**, and the vault's own "the meta block is the source of truth, not the heading" rule was quietly inverted. Fixed 31 JUL 2026 (deferred_decisions 10): the fallback now stops at any `#`/`##`-level heading, so an entry past a boundary reports `generation: None` — honest, and visible to `NEEDS_META`. An explicit value always wins; write one.
- `fs` — FamilySearch PID, or `TBD` (not-yet-searched) / `none` (searched, no profile) / **`~PID` (searched, a profile EXISTS and was REJECTED)**. Optionally `wt` (WikiTree), `anc` (Ancestry), etc. These are EXTERNAL pointers for lookup — **never the identity key** (FS PIDs rot on merges; the vault spans many sources). All optional; an entry with no `fs` is fully valid as long as it has `id` + `generation`.
  - **⚠ `none` AND `~PID` ARE OPPOSITE INSTRUCTIONS, WHICH IS WHY THE FOURTH STATE EXISTS** (deferred_decisions 41, option 2, operator-directed 02 AUG 2026). `none` means nothing is there, so **creating that person on FamilySearch is the correct next action**. `~PID` means something IS there and the vault declined it — a conflicting profile, an unreliable structure, the wrong man — so **creating would push a DUPLICATE onto a shared public tree**. Before the split both wore `none`, and a create-and-attach write-back was proposed on the strength of the bare value and withdrawn only because someone happened to read the entry prose, which said *"FS: none adopted (the FS profile at this position conflicts)"*.
  - **The `~` is the same convention as `~locator` in rule 8**: a thing you have deliberately declined is **RECORDED, not erased**. And **the PID is the point** — a rejection with no identifier cannot be re-checked by anyone, so it decays into an unfalsifiable claim. Write the reason in the entry prose alongside it.
  - **Read this field through `person_store.external_id_state()` / `live_external_id()`, never with a literal `not in ("TBD","none")` test.** A `~`-prefixed PID is a well-formed PID, so a literal screen calls it LIVE and acts on it — that is exactly the bug the helper exists to prevent, and it is pinned with negative controls in `scripts/test_rejected_external_ids.py`. `harvestable_pid()`, the deferred-38 re-check gate, the roster and the profile-review `fs_state` all delegate to it.
- `fs_private_keys` — **living-person FS PIDs (used INSTEAD OF `fs` for living people).** On FamilySearch a *deceased* person has ONE shared PID on the Global tree (that goes in `fs`); a *living* person has NO public PID and instead a **separate private PID in every tree they appear in** (the Global tree and each private Group Tree). So a living person's PIDs are a **single-quoted YAML flow-list, unlabeled** (do NOT create a per-tree key): `fs_private_keys: '[AAAA-AAA, BBBB-BBB]'`. The tree each PID belongs to is **disambiguated at access time** (navigate the tree and resolve), not encoded in the vault — the list is just the set of known private PIDs for that person. A living entry uses `fs_private_keys` and omits `fs` (so `gen_person_index` reports an empty `pid`, correct: no public PID); this also keeps living people out of the `harvest_sources` PID-bearing target set. A PID that turns out stale (e.g. the person was deleted from that Group Tree) can be pruned from the list. Deliberately a flat list, not per-tree keys.
- `parents`, `spouse`, `flags` — Phase 2 edges. **`parents`/`spouse` = single-quoted YAML flow-lists of vault `id`s** (NEVER names/dates/external PIDs), e.g. `parents: '[P-A, P-B]', spouse: '[P-C]'`. **A trailing `?` on an id marks that edge as NOT YET FS-CONFIRMED** (`parents: '[P-A?, P-B?]'`) — regardless of source: GEDCOM-seeded OR vault-authored (hand-derived from the narrative). The `?` is the verification worklist marker: any edge not yet cross-checked against FamilySearch carries a `?` so it counts as unverified rather than silently-done (this is what keeps the prompt-18 metric honest). The FS-walk verification pass drops the `?` per edge as it confirms against FamilySearch, and LEAVES the `?` on FS-GAP edges that are correct but not yet on FS (e.g. a parent who is `fs: none`, or a relative FS hasn't linked). `flags` = `Q##`, `dup`. **Do not hand-author GEDCOM-seedable edges — generate with `scripts/build_edges.py`** (GEDCOM seed → id edges; idempotent upsert/merge; `--apply` writes, default is write-preview); when you DO hand-author an edge from the vault narrative (a person/relative absent from the GEDCOM or from FS), write it WITH a `?` so it enters the verification worklist. Values containing commas/brackets MUST be single-quoted (YAML flow-mapping rule). Phase-2 GEDCOM-seed pass done 25 JUN 2026 (~23% parent coverage); FS-walk verify/fill pass worked 22-23 JUL 2026 (see below).
  - **⚠ THE `?` IS OVERLOADED, AND AN FS-WALK MUST NOT STRIP IT BLINDLY.** As written above, `?` means "not yet FS-confirmed", and the FS-walk is told to drop it on confirmation. But the same mark also gets used to record a **scholarly hedge** — an edge that FamilySearch *does* assert and that the best independent authority doubts. Those are opposite situations wearing the same mark, and a mechanical pass would silently delete documented caveats. Expect this on medieval and peerage lines, where an entry may say in so many words that FS links the couple and the `?` reflects the scholarly doubt rather than a missing FS link.
  - **Before dropping any `?`, read the entry.** If the prose gives a source-based reason for doubt, the `?` is a VERDICT and stays no matter what FamilySearch shows.
  - **Three distinct reasons a `?` survives an FS-walk**, all legitimate, none a defect: (a) **FS-GAP** — the edge is right but FamilySearch has not linked it, or a parent is `fs: none`/`TBD` (a common shape: an FS couple that lists only some of their known children, or a child absent from both parents' child lists); (b) **SCHOLARLY HEDGE** — as above; (c) **PRIVACY** — either endpoint is `life_status: living`/`unknown`, which is never web-searched at all. Only a `?` that is none of these is actionable. Report the breakdown, because the honest denominator is much smaller than the raw count — in one measured pass fewer than half the unverified parent edges were FS-checkable at all, the rest being unclearable by construction.
  - **⚠ AN EDGE TOKEN THAT IS NOT ID-SHAPED IS A `MALFORMED_EDGE_REF`, AND UNTIL 31 JUL 2026 IT WAS INVISIBLE** (deferred_decisions 8). The DANGLING check only ever noticed a *well-formed but absent* id; a token that was not id-shaped at all — a typo, or a scripted placeholder — matched no extractor and was counted as **nothing**. `parents: '[NOT_AN_ID]'` reported 0 dangling, 0 structural, a fully green tree. It nearly shipped twice, caught both times only by a hand grep for the placeholder string, and the **write-then-mint-then-wire order is unavoidable for a multi-person batch**, so it would have kept recurring. `build_edges --validate` now splits each edge value into its literal tokens and judges every one against the strict grammar (`P-` + exactly **6** Crockford chars, no I/L/O/U); a failure is **structural**, baseline 0, pinned with negative controls in `scripts/test_build_edges.py`. Note the two regexes are deliberately different: the EXTRACTOR stays loose so the writer can preserve a legacy id it did not mint, and only the JUDGE is strict.
- `adjudicated` — **the far-end ids of `?`-marked edges on THIS entry that have been WALKED AND JUDGED, with the `?` retained deliberately.** Single-quoted YAML flow-list of ids, same shape as `parents`/`spouse`: `adjudicated: '[P-G4C4Z5]'`. Absence = nothing adjudicated. Added 01 AUG 2026 (deferred_decisions 32, operator-directed).
  - **THE PROBLEM IT SOLVES: a `?` means two opposite things and nothing could tell them apart.** "Nobody has checked this" and "somebody checked it and the `?` is CORRECT" (an FS-GAP, a SCHOLARLY HEDGE, or PRIVACY) wear the identical mark, so `session_plan`'s VERIFY builder — which keyed on the mark — re-offered settled work every session. (VERIFY was collapsed into IMPROVE on 02 AUG 2026; the builder is now the IMPROVE **defect** pool, and deferred 39 records why keying a lane on this mark was the deeper mistake.) Measured on the reference vault: of 135 `?` edges only **35 were FS-checkable at all**, and **5 of those had already been judged**; two more carried hedges written in ordinary prose that no pattern matches. That last group is why the marker has to live in the DATA: a builder cannot read a paragraph.
  - **AND IT IS WHAT MAKES THAT WORK COUNTABLE.** The lane target is a floor in PEOPLE (operator, 01 AUG 2026: at least 1.5% of the vault per draw, the same in every lane), and `22-research-iterations` requires a disposition to REMOVE the person from the pool — *"prose alone is not a disposition"*. So adjudicating an edge and correctly keeping its `?` left the row in the pool for ever and **could never count toward the floor**, however much work it took. Writing the id here is what closes that.
  - **⚠ WHY NOT A THIRD TOKEN STATE (`P-XXXXXX?!`), WHICH IS THE OBVIOUS DESIGN.** `build_edges.edge_value` REGENERATES every edge token as `pid + ("" if verified else "?")`. Any suffix beyond the bare `?` is therefore **silently destroyed by the next `build_edges --apply`** — data loss with no error and no gate. `upsert_edges` splices `parents:`/`spouse:` *"WITHOUT disturbing any other field"*, so a sibling key survives by construction. Both halves are pinned in `scripts/test_adjudicated_edges.py`.
  - **Consumers.** `session_plan.py` subtracts adjudicated edges from the IMPROVE **defect** draw (was VERIFY); `--include-adjudicated` brings them back for an audit pass. `build_edges --validate` reports **`ADJUDICATED_STALE`** (advisory, baseline 0) — an id listed here that the entry no longer marks `?`, which happens when the edge is later cleared and the note is left behind. **A stale entry HIDES a real candidate**, which is the one failure mode this key can introduce.
  - ⭐ **`adjudicated_why` RECORDS *WHY*, AND THE REASON IS WHAT DECIDES WHETHER THE JUDGEMENT CAN EVER GO STALE** (deferred 38, 02 AUG 2026). Values: **`fs-gap`** / **`hedge`** / **`contradicted`** / **`privacy`**. Without it nothing can tell a permanent stop from an unread article, and `build_edges --validate` reports **`ADJUDICATED_UNEXPLAINED`** (advisory) for an `adjudicated` with no reason — 12 of 47 at the time it was added.
  - **ONLY `fs-gap` WITH A LIVE FS PID AT THE FAR END IS EVER RE-OFFERED, and the measurement is why.** A blanket expiry clock was proposed and rejected on the numbers: across 47 adjudications a clock helps **seven**. A **hedge** expires when the named resolver is READ and a **contradiction** when the sources are adjudicated — both EVENTS a clock cannot detect, and both already tracked as `Open_Questions`. Of the 24 `fs-gap` rows only 7 end at a person with a real PID; the other 28 end at `fs: none`/`TBD`, where re-checking means a **full existence probe with identifier rejection** (an FS tree search never returns zero) — i.e. re-running the expensive work the adjudication exists to record. Those 7 are re-offered as a labelled **RE-CHECK** row ranked LAST, spaced by the existing offer cooldown; **no new clock and no date key were added.**
  - ⭐ **`no-second-parent` IS A FIFTH REASON, AND IT DESCRIBES AN ABSENCE RATHER THAN AN EDGE** (deferred 50, operator-directed 04 AUG 2026). It says: *this entry names ONE parent and that is CORRECT* — a natural child, an unnamed mistress, a mother the record never gives. It is the declaration that retires a row from the `HALF_WIRED_PARENT` worklist.
    - ⚠ **It stands ALONE, with NO `adjudicated` list, and it must.** The other four reasons explain why a `?` edge survived, so they pair with a far-end id. **An absent parent has no far-end id** — that is the whole point — so writing one would be a lie, and would trip `ADJUDICATED_STALE`. A bare `adjudicated_why` with no `adjudicated` is valid only for this value.
    - ⚠⚠ **THE KEY IS THEREFORE MULTI-VALUED, AND WRITING IT AS A BARE COMMA LIST IS A SILENT-DATA-LOSS TRAP.** Measured at adoption: **14 of the 109 half-wired rows already carried an `adjudicated_why`** (`fs-gap`, `hedge`, `contradicted`) with a real `adjudicated` beside it, so a scalar could not hold both and overwriting one would switch off that row's re-check. But `adjudicated_why: fs-gap, no-second-parent` is **invalid** — the meta block is a YAML flow-mapping, so a comma'd value MUST be single-quoted — and the reader that consumed this key was `adjudicated_why:\s*([a-z\-]+)`, which **does not match a leading quote at all**: the row would have parsed as having NO reason while the entry advertised one. Same shape as the `P-XXXXXX?!` suffix that `adjudicated` was designed to avoid.
    - **So both forms are legal and a conforming reader takes BOTH**: the bare scalar `adjudicated_why: fs-gap` (what all 46 existing rows use, not migrated) and the single-quoted list `adjudicated_why: '[fs-gap, no-second-parent]'`. **Read it with `person_store.adjudicated_why_values()`, never with a regex** — one home for the grammar, and `build_edges --validate` and `session_plan.lane_defects` both go through it so the gate and the lane cannot disagree. Unrecognised tokens are dropped, so a typo cannot invent a reason. Pinned with negative controls in `scripts/test_adjudicated_why.py`.
    - ⛔ **Declare it only from a RECORD or a named authority, never from the graph.** The triage that produced this value found a mechanical scan proposing a father's SPOUSE as the missing mother — on **Robert FitzRoy**, natural son of Henry I, where the spouse offered was Henry's queen. Charlemagne had four wives and Hildegard was the second; **any rule that closes a parent edge from a spouse edge picks the wrong woman whenever there was a remarriage.**
  - **Write it only for an edge you have READ and judged.** The seeding pass found an entry whose note said its *maiden surname* was unconfirmed — not a verdict on its parent edge — and marking it would have suppressed genuine work. The prose must say the edge was walked and the `?` kept on purpose.

- `fs_probed` / `route` — **"FamilySearch was checked and is EMPTY, and the records are actually over THERE."** `fs_probed` is an ISO date (`2026-08-03`); `route` is a short slug naming where the evidence lives — a registered host id (`metryki`, `jri`, `geshergalicia`, `antenati`) or an archive slug where the route is in-person (`como-diocesan`, `aquila-diocesan`, `as-sondrio`). Both optional, both meaningful alone. Added 07 AUG 2026 (operator-directed; [[Open_Questions]] Q157 + `deferred_decisions` 51).
  - ⭐⭐ **THE PRIMITIVE THAT WAS MISSING.** The vault could say *"this person cannot be sourced"* (`structural_gap`) and *"no profile exists"* (`fs: none`). It could NOT say **"this person CAN be sourced, just not here"** — so six people whose records demonstrably exist (four died AFTER civil registration began; one lived 1876-1937; one is Galician, a different regime entirely) had nowhere to go but an opaque `pids` enumeration in `structural_gap` rule 3, which is the enumeration pattern the operator ruled against on 05 AUG 2026 in favour of stating the CRITERION.
  - ⭐⭐ **AND `structural_gap` NEVER RETIRED ANYBODY — measured 07 AUG 2026.** It moves a person from `SOURCE_GAP` into `BOOK_SOURCED` or `UNCITED`, and **both are live ROTATE arms**. Their hit rates are **0.17 and 0.15** against **0.43-0.48** for every other arm, and they are **355 of the 1,386 rotation pool (26%)**. The vault was declaring "FamilySearch will never have this person" and then polling FamilySearch for them, ~1 poll in 4. Two rows were re-polled in a single sitting for exactly this reason.
  - ⚠ **`fs_probed` IS NOT `fs: none`.** `fs: none` says no PROFILE exists. `fs_probed` says the attached-source set was read and holds **NO RECORDS** — a positive read at the `entityref` endpoint, which is a stronger statement than a failed render. A person may hold a live PID and `fs_probed` on the same day.
  - ⭐⭐ **"EMPTY" MEANS NO *RECORDS*, NOT NO *ATTACHMENTS* (operator ruling 07 AUG 2026, `deferred_decisions` 52).** An attachment that is a **book, a memorial, a user tree, a reference work or a legacy NFS stub** is not a record (rule 8 limbs (c), (d), (e), and the reference-work class), so a profile carrying twenty of them and zero record ARKs **is empty for this purpose and earns `fs_probed`**.
    - **The literal reading was measured and rejected because it excludes the population the key exists for.** One session polled 63 rows and hit the shape three times in twenty: an 11th-century king at **29 attachments / 0 records** (a memorial index entry and a foreign 20th-century US vital-record index), a 13th-century noblewoman at **19 / 0** (two memorial entries for someone dead in 1248, plus 17 books), and a 10th-century Irish king at **5 / 0** (five copies of one legacy tree stub). Under "no attachments" none of the three could ever be declared, and the vault would go on polling FamilySearch for people it had already concluded FamilySearch will never document — which is the exact waste `structural_gap` failed to stop.
    - ⚠ **THE COST, AND IT IS REAL: THE KEY NOW DEPENDS ON A CLASSIFICATION, NOT ON A COUNT.** A raw attachment count cannot be got wrong; "does this profile hold a record" can. So a `fs_probed` written under this rule **is only as good as the title screening behind it** — screen with `harvest_sources.is_book_collection` / `is_memorial_collection` / `is_obituary_collection` / `reference_work_limb`, never by eye, and ⛔ **never by treating the unrecognised residual as records** (that is the residual-bucket error, and it inflates hardest on exactly these deep rows).
    - ⭐ **Say in the entry prose WHAT was read**, not merely that a probe happened — "29 attachments, 2 ARKs, one Find a Grave and one foreign 1980 Kentucky index" is auditable; "probed, empty" is not. The date says *when*; only the prose says *on what basis*, and this ruling makes the basis the part that can be wrong.
    - **The unambiguous case still exists and is worth keeping as a control:** a live PID with genuinely **zero attachments** (a Gen-6 collateral row on a Polish line) qualifies under either reading, so it is the row to test a future change against.
  - ⚠ **THE DATE IS THE POINT.** An undated negative is treated as expired on sight, so the row returns every rotation for ever — the defect that put two rows back in the EXISTENCE_PROBE arm in one sitting with nothing to learn — a 9th-century woman whose only relative is also `fs: none`, and a toddler who died in 1863 in a comune with no FS coverage. **Do not write `fs_probed` for a probe you did not perform**; an invented date is worse than no date, because it silences a real worklist row.
  - ⚠ **AN UNRECOGNISED `route` SLUG IS RETURNED, NOT DROPPED — deliberately the OPPOSITE of `adjudicated_why_values`.** That vocabulary is tiny and closed, so swallowing a typo is safe. Routes are open-ended (every archive in the world), so dropping an unknown would make a declaration **silently fail**, which is the exact failure this key exists to remove. Shape is enforced (lowercase slug, 2-40 chars) so prose cannot become a route; a validator may WARN on an unknown slug, but the reader must not swallow it.
  - **Read them with `person_store.fs_probed()` / `person_store.route()`, never by regex** — one home for the grammar, the same rule as `adjudicated_why_values` and `banked_parents_host`. Both are UNMODELED keys, so `_record_to_meta` preserves them and a narrative⇄file conversion round-trips them. Write with `person_store.set_meta_key`. Pinned with negative controls in `scripts/test_route_declaration.py`.
  - ✅ **WIRED INTO THE BUILDERS 07 AUG 2026.** `profile_review` now retires a **BOOK_SOURCED** or **UNCITED** row that carries a `route`: for those two arms the poll is *"is the non-FS route NAMED?"*, so a declared row has answered it and leaves the eligible pool. Constant `ROUTE_RETIRING_ARMS`; pinned with negative controls in `scripts/test_profile_review.py`.
    - **The filter lives in `allocate()`, NOT in `build_candidates()`**, so the arm's `pool` keeps reporting its true size while `eligible` shrinks, and the draw prints a **`rtrd`** column plus a per-arm `retired_by_route`. Retiring by dropping candidates would make the arm appear to shrink and leave nobody able to see how many rows were settled.
    - ⚠ **RETIREMENT IS PERMANENT FOR THOSE ARMS AND HAS NO COOLDOWN** — `route` is a standing declaration about where the evidence IS, not a dated negative. If the route is later worked, the person's CATEGORY changes and they re-enter the rotation through a different arm on their own.
    - ⛔ **`fs_probed` DELIBERATELY DOES NOT RETIRE ANYTHING.** It is a DATED point-in-time reading, which is cooldown-shaped rather than retirement-shaped; treating it as permanent would let a stale probe silence a row for ever. It is carried onto the candidate for display only, and that exclusion is pinned by a test so it is not "fixed" by accident.
    - ⭐⭐ **A TERMINUS IS NOT A MISSING ROUTE. THE TWO ARE ORTHOGONAL, AND CONFUSING THEM COSTS A WHOLE ARM** (measured 07 AUG 2026, `deferred_decisions` 53). A **terminus** is about **ANCESTRY** — the line goes no further up. A **route** is about **DOCUMENTATION** — where the evidence for *this person* lives. A person can be exhaustively documented and still be a dead end, and on medieval lines most are: the clearest case is an apex row whose terminus statement is **itself sourced to Medlands**, the same work being both the route to the man and the authority that his parentage is unknown.
      - **Measured across the class: of 262 `BOOK_SOURCED` rows, ZERO are termini in the route sense.** All 262 cite apparatus — necessarily, since `BOOK_SOURCED` *is* "0 ARKs and cites scholarly apparatus", so that figure is a positive control rather than a finding. Of the 29 whose prose carries terminus language, **22 are about ancestry or depth, 6 were false matches on a log FILENAME containing "terminus"**, and 1 was a bullet written that same day asserting the class existed.
      - ⛔ **So do NOT withhold a `route` because an entry says "terminus", "ceiling" or "brick wall".** Ask only: *does a named work document this person?* For a `BOOK_SOURCED` row the answer is yes by construction — the category is assigned by finding that citation.
      - ✅ **CONSEQUENCE, TAKEN 07 AUG 2026 (operator-directed): the whole `BOOK_SOURCED` arm was declared in one pass** — a route derived mechanically for every row from the apparatus it already cites, since the census reads that same citation to assign the category. The arm now stands at **pool 262 / eligible 0** and is complete. ⚠ **This is a legitimate exception to "never bulk-declare", and the reason it is legitimate is that the REASON was not invented**: each slug restates a citation already in the entry. A bulk declaration whose reason has to be supplied by the declarer is still forbidden.
      - ⚠ **Derive from the MOST SPECIFIC work cited, not the broadest.** Cawley/Medlands is a catch-all that a majority of medieval entries cite in passing, so ordering it first swallows rows whose real resolver is a named chronicle (Flodoard, Regino, the *Primary Chronicle*) or a targeted reference (*Complete Peerage*, ODNB, the Henry Project, a Visitation). Put the specific works ahead of it in the mapping.
      - ⚠ **AN ARM THAT IS FULLY DECLARED IS "FLOOR UNMET" FOR A DIFFERENT REASON THAN A COLD ONE, AND THE REPORT MUST SAY WHICH.** `profile_review`'s floor-unmet line used to assert *"every candidate in that arm is inside its cooldown"* for every unmet arm; once an arm could be permanently declared that became false, and a settled arm reported as a cold one sends the next reader hunting a rotation bug that does not exist. The cause is now computed per arm and pinned in both directions.

- `banked_parents` — **the host on which this person's parents were LOCATED and deliberately NOT WIRED.** Scalar, one of `fs` / `wt` / `anc`; absence = nothing banked. Added 04 AUG 2026 (operator-directed).
  - **WHY IT EXISTS, and it is a measured hole, not a tidiness.** An EXPAND draw that finds a frontier row's parents named on FamilySearch correctly declines to wire them — **an FS couple is a TREE ASSERTION, not a source**, and wiring it grows the vault on somebody else's conclusion. The row is then DECLARED, so `extension_frontier` counts it CLOSED and **EXPAND never offers it again** — while the work is real, located and cheap (find one record naming the parents, then wire with a `?`). Measured at adoption: **11 rows, 7 from session #138 and 4 from #139, holding ~22 parent PIDs, none of those parents in the vault**, growing 7 → 11 in two sittings with nothing drawing it. **The same shape as the FS write-back queue: found work with no lane.**
  - **It is a drawable IMPROVE sub-population** — `session_plan.lane_banked()` feeds the DEFECT pool as the `banked` tier, ranked **below `edge`** (a `?` edge is a claim the tree has already adopted) and **above `audit`** (a banked pair is the most specific work in the pool: the parents are named, dated and PID'd). Its disposition is the defect unit, `--verified`.
  - ⚠ **SELECTED FROM THE DATA, NEVER FROM THE DECLARATION PROSE.** The obvious detector is a grep for the declaration wording, and this vault has already ruled against exactly that: rule 8 limb (g) considered making a bullet NAME load-bearing and **did not take it** — "it would make bullet TEXT a failure surface, where a typo silently starts counting". A prose scan also **double-counts**, because `route_digest` blockquotes entry text at the head of every lineage file: the first count taken while designing this read **27 declarations where the truth was 11**, the identical trap the `? edge` grep documents. Read it with **`person_store.banked_parents_host()`**, the one home for the grammar.
  - ⚠ **A SCALAR, NOT A LIST OF PIDs.** The lane needs to SELECT the row; the researcher needs the PIDs, and those are already in the entry's frontier declaration where they are read. Storing them twice creates a second copy to drift. The value is the HOST so the key generalises past FamilySearch without a grammar change.
  - **The exit test is the `parents` EDGE, not the key** — a wired row is never offered even if the key is left behind. That residue is reported as **`BANKED_STALE`** by `build_edges --validate` (advisory, baseline 0): prune the key when you wire the edge.
  - ⭐⭐ **WIRING A BANKED PAIR MOVES THREE COUNTS THE "WRONG" WAY AT ONCE, AND ALL THREE ARE HONEST.** The row gains a `parents` edge, so it leaves the frontier population entirely (**DECLARED −1**); its two parents arrive parentless (**SILENT +2**); they arrive at 0 own records, because a record naming the parents documents the CHILD and is limb (g) `Named-in`, off the census (**SOURCE_GAP +2**); and both new edges are wired unverified (**+2 `?` tokens**). On the 11-row backlog measured at adoption — each naming exactly 2 parents, none already in the vault — draining it fully would read **DECLARED 311 → 300, SILENT 244 → 266, SOURCE_GAP 167 → up to 189, `?` 88 → 110**. ⭐ SILENT 266 is *exactly* where it stood before the EXPAND iteration that created the backlog, which is the clearest possible statement that this is circulation, not loss.
  - ⚠ **`22-research-iterations` carries the guard, and it is PER-EFFECT, NOT PER-LANE.** It named EXPAND alone until 04 AUG 2026, because until then only EXPAND minted parents. Now IMPROVE does too, so **a lane whose own metric is SOURCE_GAP routinely pushes SILENT up** — and under the standing rule that a non-zero gate is a REGRESSION rather than a backlog, an unexplained rise reads as damage and gets investigated at real cost. ⛔ **Do NOT pre-declare the minted parents to hold SILENT flat**: that is "never bulk-declare to reach 0", and a declaration inherits the correctness of its REASON. ⚠ It is also a **cross-lane effect the bandit does not model** — an IMPROVE draw scoring a legitimate hit inflates EXPAND's backlog. The lanes are a small economy, not independent arms.
  - ⚠ **Safe as an UNMODELED key, and that was verified rather than assumed.** `_record_to_meta` preserves "any UNMODELED keys the original block carried", the file backend's frontmatter write is likewise surgical, and `upsert_edges` splices `parents:`/`spouse:` without disturbing siblings — the same three guarantees that make `adjudicated` safe, and the reason the `P-XXXXXX?!` token design was rejected for it. Pinned, including the `upsert_edges` survival case, in `scripts/test_banked_parents.py`. **Bank it with `person_store.set_meta_key`, never by splicing text.**
  - ⭐⭐ **THERE ARE NO "EFFORT" STOPS. A FRONTIER DECLARATION IS ABOUT ANCESTRY, NEVER ABOUT WORK NOT YET DONE** (operator ruling, 07 AUG 2026). A **DECLARED** row means the line goes no further up *on some authority*. It does **not** mean nobody has got round to it. Those are opposite states, and the vault had been recording both in the same field:
    - a **TERMINUS** is about **ANCESTRY** — no cited authority carries the line further (Rollo, whose parentage Cawley calls uncertain; Rurik, reconstructed solely from the 12th-c *Primary Chronicle*).
    - a **STOP** is about **EFFORT** — the work is simply undone. **That is a research to-do, which is exactly what SILENT is for.**
    - ⚠ It is the same orthogonality as deferred 53 (a terminus is not a missing route), one axis over: **a terminus is not a to-do either.**
  - **CONSEQUENCE, TAKEN 07 AUG 2026:** `extension_frontier.DECLARED_RE` no longer matches `NOT WORKED` / `not yet worked` / `deliberate stop` / `NOT EXTENDED` / `do NOT adopt|extend|wire`. **Measured: 39 of 327 declared rows rested on that language ALONE and became SILENT** (SILENT 238 → 277, DECLARED 328 → 289, total parentless unchanged at 566 — pure reclassification, nothing found or lost). Pinned with negative controls in `scripts/test_frontier_declaration.py`.
  - ⛔ **AND IT REVERSES THE OLD COST ARGUMENT, WHICH WAS WRITTEN INTO THAT FILE.** The comment used to reason that *"a false DECLARED is cheaper than a false SILENT"*. It is not. A false SILENT merely nags; **a false DECLARED removes a real row from the EXPAND pool permanently and silently, and nothing ever re-examines it.** Two were minted by accident in a single sitting (deferred 55) — one by a bullet reading *"Bank, do not wire from the tree"*, a statement about METHOD that closed a frontier row.
  - ⚠ **THE RESIDUAL HAZARD IS NAMED RATHER THAN FIXED.** The free-text ancestry phrases still match, and *"her parentage is unknown"* is written both about a **closed** question and about an **open** one — no regex separates those. **The explicit `FRONTIER DECLARATION <date>` marker is the only unambiguous form; prefer it.** If a stop is real, say which authority carries it.
  - **PEDIGREE COLLAPSE IS DECLARED, NOT RENUMBERED** (deferred_decisions 16, settled 31 JUL 2026). When a vault descends from one couple by two paths of different length, the shorter path fixes the descendant's `generation` and the longer fixes the ancestor's, so `parent != child gen + 1` on the edge between them **while every edge is correct**. The settled reading: **`generation` is a PATH label, not a global depth.** Do not renumber a branch to make the advisory tidy — the cascade reaches far past the rows you meant to fix. Declare the affected edges in the vault's `.autoresearch.json` `known_gen_collapse` (`{child, parent, note}`, read via `vault_config.get_known_gen_collapse`), and annotate all three entries involved so nobody "corrects" it later. `build_edges --validate` then reports them as **`GEN_COLLAPSE` (expected)** and leaves **`PARENT-GEN MISMATCH` meaning UNEXPLAINED**, which is the whole point: before the split the count silently mixed known collapse with real generation bugs and neither could be read. **Never bulk-declare rows to drive the count to 0** — that recreates the blindness.

### The bold-name HEADER also has a grammar

The `- meta:` block above is machine-grade. The **header beside it was not** — it was
free prose a parser had to guess at, eight dialects accumulated, and the guessing
wrote 25 wrong dates into this vault before an audit caught them. The corrective is
at the WRITE end. **`header_audit.py --changed-only` runs in the vault pre-commit
hook and BLOCKS any header this commit writes or edits** (the ~750-entry legacy
backlog stays advisory until the Spec 04 migration).

```
**[Name]** (<field>; <field>; …)   [free prose after the paren]
```

**The rule constrains the DATE SLOT, not the sentence:** a `b.`/`bapt.`/`chr.`/`d.`
field carries a GEDCOM 7 `DateValue` or the literal `unknown`; the place follows the
date behind a comma; no parenthesis inside the date slot; and no vital field is
required when the meta block carries no `born`/`died`. **The five write-time rules,
with worked examples and the defect each one prevents, are
[workflows/header-grammar.md](workflows/header-grammar.md) §"Writing a header by
hand" — read it before hand-authoring a header.**

**Everything else in the header stays free prose — deliberately, including when it
contains a year.** `Gen 35`, `a weaver`, `alive 1852` (a floruit), `atto 534`, an
editorial aside: all legal and all unread, because a conforming reader only looks
inside a declared date slot. That is the entire point. Do NOT "helpfully" convert a
floruit or a document number into a vital field — those exact values are what the
old positional guessing turned into births.

Copy-paste shape: [vault-template/templates/person_narrative.md](vault-template/templates/person_narrative.md).
Full grammar, rationale and the migration runbook:
[workflows/header-grammar.md](workflows/header-grammar.md).

### Dates (`born` / `died` / `born_phrase` / `died_phrase`)

Dates are a **record field**, not prose
recovered by regex. The value grammar is the [GEDCOM 7 `DateValue`](https://gedcom.io/specifications/FamilySearchGEDCOMv7.html),
which exists precisely for genealogical dates; a bare ISO `YYYY-MM-DD` is also accepted
on read. Validate one value with `python3 scripts/gdate.py '~1750'`. **The full
production list — plain year through `ABT`/`EST`/`CAL`, bounds, spans, non-Gregorian
calendars and epochs, each with when to reach for it — is
[workflows/structured-dates.md](workflows/structured-dates.md) §"Writing a date by
hand".**

Values are single-quoted in the meta flow-mapping:

```
- meta: {id: P-XXXXXX, …, generation: 8, fs: XXXX-XXX, born: '3 SEP 1780', died: 'BET 1816 AND 13 FEB 1823'}
```

Four rules, each of which exists because breaking it caused a real defect:

1. **Omit the key when the date is unknown.** Absence = unknown, the same convention
   `evidence_tier` uses. Never store `unknown` / `Deceased` / `?` as a *value*.
2. **Places stay OUT of the date value.** The header keeps `date, place` for humans.
   `prose_audit` takes the PLACE from the header and the YEAR from the field; deriving
   a place from a date field is a category error that produced a live false positive.
3. **`EST`, not `ABT`, for a declarant-age-derived year.** That puts this vault's
   "declarant-age estimates are ESTIMATES, not facts" rule *in the data* instead of in
   a prose caveat.
   - ⭐⭐ **THE DISCRIMINATOR IS "CALCULATED FROM OTHER DATA", NOT "HOW VAGUE THE INPUT WAS"**
     (operator supplied the GEDCOM 7 definitions, 07 AUG 2026). Verbatim: **`ABT x`** = *exact
     date unknown, but near x*; **`CAL x`** = *x is calculated from other data*; **`EST x`** =
     *exact date unknown, but near x; **and** x is calculated from other data*. So **EST is
     literally ABT + CAL**, and the test is a single question: **was `x` DERIVED?**

     | the value was… | approximate | derived from other data | use |
     |---|---|---|---|
     | a rough guess, nothing computed | ✔ | ✘ | **`ABT`** |
     | computed, and you believe the result is exact | ✘ | ✔ | **`CAL`** |
     | computed, result still approximate | ✔ | ✔ | **`EST`** |

   - ⛔ **DO NOT reason "the input was itself approximate, so ABT and EST are both defensible."**
     That argument was made in this vault about a Gen-14 row whose entry says *"approximately 21
     years old"* at a dated event, and it is **wrong**: (event year − stated age) is a
     calculation whatever the precision of the age, so the row is `EST`. **The vagueness of the
     input is what separates `EST` from `CAL`, not what excuses `ABT`.**
   - ⚠ **`CAL` is the value this vault most likely under-uses.** A birth date computed *exactly*
     — from a death date plus an age given in years, months and days, say — is `CAL`, not `EST`,
     because nothing about it is approximate. No gate can see the difference.
   - ⚠ **NOTHING WILL EVER FLAG A WRONG ONE.** `ABT`, `EST` and `CAL` all normalise to the same
     comparable year, so `DATE_DRIFT` and every other date gate are blind to the distinction.
     It is correct only if it is written correctly the first time.
4. **Old Style / New Style dual dates use BOTH keys, and the DATE takes the NEW STYLE
   (later) year** — GEDCOM 7 Appendix A §6.2's own worked example. Taking the earlier
   year is the intuitive choice and it is wrong; it silently backdates every
   January-to-March event by a year.

```
- meta: {id: P-XXXXXX, …, born: 'JULIAN 30 JAN 1649', born_phrase: '30 January 1648/49'}
```

The header parenthetical is unchanged and stays human-authored — it carries what a
structured field cannot (`near Weymouth, MA`, `killed King Philip's War`,
`christened 3 SEP 1676`). The two are kept honest by the advisory **`DATE_DRIFT`**
metric, which compares their YEARS (integrity rule 7).

## Vault Integrity Rules

When adding or modifying person entries in any Family_Tree file:

1. **Single-generation headings only.** Every `### Generation N:` heading must use a single number, never a range. If a section would span multiple generations, split it into separate headings grouped by lineage (e.g., `### Generation 12: Smith / Jones (Anytown, County)`).

2. **Assign a generation number to every person.** Generation counts from the subject (Gen 1). Before adding a person, trace the shortest path from Gen 1 to determine their generation. Do not guess from the section they "feel like" they belong in.

3. **No duplicate person entries.** Before adding a person, grep the target Family_Tree file for their name. If they already exist, merge new information (FS PIDs, children lists, source details) into the existing entry. Never create a second entry in a different section.

4. **Every new person entry gets a `- meta:` flow-mapping in the same commit (this replaces the retired "update Person_Index" rule).** A person added to a Family_Tree file must carry a `- meta: {…}` block as its first body bullet with at least `id` + `generation` (`evidence_tier`/`profile_status`/`life_status`/`fs` recommended). Mint the `id` mechanically with `python3 scripts/mint_ids.py --apply`. There is no second store to keep in sync — the narrative + its meta block IS the record. The gen-sorted roster regenerates on demand (`gen_person_index.py --write`).

5. **Verify before committing.** The checks and their commands are the `person-entry` and `audit-gates` skills; the pre-commit hook enforces the HARD ones (`gen_person_index --integrity` must report 0). The one check no gate performs, so do it by hand: **grep the target file for each new person's name before adding them**, and merge into the existing entry if found.

6. **Header lines carry ONLY the entry's own FS PID — no cross-reference PIDs in the bold-name header.** Do not put another person's PID (spouse / parent / child / sibling) on the same line as the bold name. Cross-reference PIDs belong in a **body bullet** (e.g., `- Married Mary Smith (FS: XXXX-XXX)`), never the header. Rationale: scripted source-bullet insertion anchors each bullet on the header's PID, so a foreign PID there causes mis-attribution — a real incident attached bullets to the wrong people, and to living relatives, because headers inlined "father John Smith XXXX-XXX"-style cross-refs. Gated by `header_xref_audit.py` (advisory). Do NOT add new violations; burn the pre-existing backlog down incrementally when editing a file for other reasons.
   - **Identity is the meta `id:`, never a name/date/external PID.** A malformed bold name is fine — entries are detected by their `- meta:` line, so a bad name can no longer make an entry invisible or duplicate it.

7. **Prose summaries must stay in sync with canonical entries — and so must the header/meta date pairing, and the header must match the header GRAMMAR.**
   - **Dates live in TWO places with different jobs**: the `- meta:` `born`/`died` FIELD is the machine value and is AUTHORITATIVE; the header parenthetical is the human display, carrying what a structured field cannot (`near Weymouth, MA`, `killed King Philip's War`). Change one, change the other in the same commit. `DATE_DRIFT` compares their YEARS, not their strings — they may differ in wording, never in fact. **BLOCKING**; `--no-strict-dates` overrides for one run. The same applies to derived prose: intro paragraphs, "Lineage interconnections", society walks and similar paraphrase the canonical entry, so when the entry changes they change in the same commit.
   - Run `python3 scripts/prose_audit.py` after editing any person's vitals, parents, spouse, generation, or PID; fix every ERROR-level issue. **Verify against the canonical entry BEFORE writing new prose** — in every drift bug this has caught (a spouse mix-up, a name typo, a generation miscount, a stale `d. ?`), the entry was right and the prose was wrong.
   - Relationship descriptors ("paternal grandmother X", "great-great-grandfather Y") are especially error-prone. Generations count from the anchor (Gen 1; your vault's anchor set is declared in its `.autoresearch.json`, and named in your local instance file if you keep one) — Gen 2 = parents, Gen 3 = grandparents, Gen 4 = great-grandparents, Gen 5 = 2nd-great, Gen 6 = 3rd-great. **The rule: for Gen N ≥ 4 the person is the (N − 3)th great-grandparent**, so Gen 14 = 11th great-grandparent. When phrasing "Generation N (her X generation)", confirm the arithmetic: subject + offset = N. *(Corrected 25 JUL 2026: this line read "Gen 6 = great-great-grandparents", which skips Gen 5 and is off by one — it understated every deep relationship by a generation. Stating the (N − 3) rule rather than an enumeration is what stops it recurring.)*
   - Session logs in `vault/logs/` are EXCLUDED from prose_audit by design — they're write-once historical research notes documenting what was known at the time, not living summaries.

8. **Source-coverage invariant.** Each PID-bearing narrative entry should cite the primary-source records (census, vital records, immigration, naturalization, etc.) that document that person. Sources are documented in the entry's **`- **Sources**`** bullet using the Spec 03 (`multi-anchor-multi-repo`) **record / host:locator grammar**: one sub-bullet per RECORD (the primary source), each carrying one or more `host:locator` pairs, e.g. `- 1910 US Census, Manhattan — fs:1:1:XXXX-XXX` or `- 1847 birth atto — antenati:ark:/12657/an_…, fs:3:1:YYYY-ZZZZ` (one record, several hosts). `host` is a short id from the **`hosts` registry** (`vault_config.DEFAULTS["hosts"]`, extended per vault via `.autoresearch.json` `hosts`) — **read it with `python3 scripts/vault_config.py <vault>` rather than trusting a list written here; an enumeration in prose is exactly what went stale.** ⚠ **REGISTERING A HOST IS THE WHOLE JOB, and since 02 AUG 2026 it actually works**: `harvest_sources.EMITTED_HOST_IDS` now DERIVES from the registry, where it used to be a hard-coded literal that disagreed with it in both directions (`anc`/`wt` counted while unregistered; anything newly registered counted for nothing, so deferred-17's "register the host" remedy was a no-op). Adding a host is now a config edit, no code change. A host may set `short` when its emitted prefix differs from its key (only `familysearch` → `fs`). ⚠ **A locator token is a NON-SPACE run**, so write `tna:C1/548/65` and `nycdoris:D-B-1921-0002748`, never with spaces.        - brother <Brother's name>'s 1707 baptism, "and <Father's name>" (their father) — ~fs:1:1:XXXX-XXX

     ⚠ **WHY RECORD SOMETHING WORTH NOTHING.** The alternative is deletion, and a deleted locator is indistinguishable from one nobody looked at — so the next reader of that Sources tab re-derives the same judgement. **The `~` says "seen and dismissed"; absence says nothing.** This is the same argument as `~locator` generally and as the `~PID` in the `fs` field.
     ⚠ **AND IT IS WHY A RAW LOCATOR LIST IS NOT A RECORD COUNT.** Limbs (g) and (h) together are most of what sits on a typical FS Sources tab: **an FS profile is closer to a HOUSEHOLD's record set than to one person's.** Measured on five people, raw ARK totals overstated their own records by **4x to 23x** (36 locators → 2 records in the worst case). **Group by the event descriptor in each citation BEFORE writing a `Sources` bullet** — the descriptor is in the same string that gives the collection title, so it is free at harvest time and expensive to recover later.
   - **WikiTree corroboration is a SEPARATE qualitative layer, NOT part of this ARK metric.** WikiTree-as-a-tree stays excluded (it copies FS, and may copy your vault — circular). But a WikiTree profile's *cited primary sources* and *analytical/disambiguation content* (Research Notes, G2G threads, "Was she X?" pages) are valuable for contested/patriot/deep Anglo entries. Capture them as a distinct `- **WikiTree corroboration** (<ID>, read <date>; off the FS-ARK coverage metric): …` narrative bullet — corroboration comes from *what WikiTree cites, never its bare assertion* — and it is **operator-gated** (WikiTree blocks anonymous reads). **The read mechanics, pacing and scope are in [prompts/19-fs-source-harvest.md](prompts/19-fs-source-harvest.md)** (migrated 05 AUG 2026).
   - **AN OUTWARD WRITE THE VAULT CANNOT PERFORM IS QUEUED ON THE ENTRY, NOT IN A LEDGER FILE** (grammar fixed 31 JUL 2026; the practice is older). Research routinely finds something FamilySearch has wrong, missing, or unattached, and every such fix is operator-gated: the session may not perform it. Record it as a bullet on the person's OWN entry, in two states:

     ```
     - **FS write-back QUEUED 31 JUL 2026** (<PID>; promote birth conclusion): FS carries year-only
       1909; the vault holds 12 OCT 1908 — evidence fs:1:1:XXXX-XXX (NYC birth record) — life_status: deceased
     - **FS write-back DONE 31 JUL 2026** (<PID>; session #123, operator keystroke): birth conclusion
       set to 12 OCT 1908, cert attached.
     - **FS write-back DROPPED 31 JUL 2026** (<PID>): superseded — a contributor had already corrected it.
     ```

     **THE GRAMMAR, and it is exact because a grep is the ledger:**

     | Slot | Rule |
     |---|---|
     | token | `FS write-back` + one of `QUEUED` / `DONE` / `DROPPED`, bolded, followed by the date. Three states, no fourth: an item that turns out not to apply is DROPPED with its reason, never deleted, or the count loses it silently. |
     | paren | `(<PID>; <action or note>)`. Semicolons inside, never commas — a comma reads as part of the PID. |
     | body | what and why, then `— evidence <host:locator>` then `— life_status: <value>`, in that order, on QUEUED. DONE says what was actually written. |
     | HELD | not a fourth state. An item waiting on something (a reply, a poll) stays QUEUED and says `— **HELD, do not act yet**` in its action. |

     **A READER MUST BE TOLERANT OF WHAT IS ALREADY WRITTEN.** Match
     case-insensitively, accept `writeback` as well as `write-back`, and ignore any
     leading check mark. This is not hypothetical politeness: when this grammar was
     adopted the corpus already held FIVE spellings, and the first counter written
     against it was case-sensitive and undercounted the DONE bullets by four. Count
     on the words; never on the decoration or the case.

     Five rules, each of which is why this shape and not another:
     - **The DONE bullet REPLACES the QUEUED one; they never both stand.** A queued action is CURRENT state (something is owed on this person); once performed it is one line of current state again, not two lines of history. Same rule as every other entry bullet.
     - **The ledger is EMERGENT: `grep -ric "FS write-back QUEUED" [VAULT]/Family_Tree*.md`.** No queue file, no meta-block key (rule 9 forbids it), no second store to drift. Match on the WORDS — some existing bullets prefix a check mark and a grep must not depend on it.
     - **Evidence and `life_status` are part of the grammar, not decoration.** Without the locator the next session re-derives the research that justified the write; without the life_status mark a living person can reach a public target. The per-target gate is `scripts/privacy_gate.py` — public targets (FamilySearch, WikiTree) DENY `living` and `unknown`.
     - **A queued item is a CANDIDATE.** An FS record hint, a "possible duplicate", a date FS disagrees with: name the identifier check that would settle it, and do not queue an action whose evidence is a same-name match.
     - **Produced by `23-session-review`, drained by `17-familysearch-tree-contribution` with the operator present.** It is deliberately NOT a session-plan lane: the standing priority is that write-back is a byproduct, not a driver, and a bandit-drawn lane of operator-gated work would stall an autonomous run the moment it was drawn.

9. **The meta block is the machine record; keep it lean. Research-history prose lives in the narrative body, not the meta block.** Each `- meta:` flow-mapping carries only the fixed-grammar fields (`id, evidence_tier, profile_status, life_status, generation, fs/wt/anc, parents, spouse, flags`). Do NOT stuff harvest provenance, dates of discovery, or relationship narration into it — that belongs in the bold-name entry's body bullets. The gen-sorted roster (the lookup the retired `Person_Index.md` used to provide) regenerates on demand: `python3 scripts/gen_person_index.py --write /tmp/roster.md`. Two sub-rules:
   - **⚠ A KEY WRITTEN TWICE IS VALID YAML AND LAST-WINS, SO IT SILENTLY DISCARDS A VALUE** (deferred 25, gated 02 AUG 2026). `- meta: {id: P-0XAMP1, fs: VVVV-VVV, …, fs: TBD}` parses fine and every reader sees `TBD`, while the entry advertises the banked PID. It surfaced ONCE, and not from a gate: a ROTATE draw listed as an EXISTENCE_PROBE a person whose FS profile the VERIFY iteration had just read and cited. **Two lanes contradicting each other was the detection mechanism.** Now `DUP_META_KEY` is a **HARD** violation in `gen_person_index --integrity` (baseline 0), and the WRITE side is `person_store.set_meta_key(line, key, value)` — **bank an external id through that, never by splicing text**, because it replaces in place (and collapses a pre-existing duplicate) instead of prepending. The gate and the record reader share one splitter (`_split_flow_items`) so they cannot disagree about where a key ends.
   - **Files stay sorted by `generation`** within each `### Generation N` section (Gen 1 first; no-generation last). Collateral/theme-organized files keep their family grouping — the gen-sorted VIEW is the generated roster, not the file order. Do not append deferred "Coverage Audit Additions" / "Recipe-N" tables — fold new people into the right section immediately, each with a meta block.
   - **Pre-commit expectation.** Which gates block, which are advisory, and how to read a non-zero: the **`audit-gates` skill**. Two notes that are policy rather than mechanics: `DUP_FS_PID` is ADVISORY (an FS PID is an external attribute, not the identity key; record the expected baseline in `.autoresearch.json` `known_dup_fs_pids`), and a known field-drift or gen-numbering backlog is a separate task, **not** a commit blocker.

## Content-boundary policy (per-lineage file routing)

A lineage that outgrows one file is split into companion shard files by content
ROLE, not just size. The reusable routing pattern:

| Content role | File |
|---|---|
| Direct-line ancestor + spouse | the lineage's main `Family_Tree_<Region>.md` |
| Immediate sibling-collateral that authenticates a direct ancestor (atto declarant/witness, primary-source kin proxy) — 1-2 line inline entry | same main file |
| Extended sibling-collateral with its own multi-source sub-pedigree; in-law deep pedigrees; surname-cluster collateral discovered via record scans | `Family_Tree_<Region>_Collateral.md` |
| Region/surname "Origins and Toponymy" essay once it crosses the shard threshold | `Family_Tree_<Region>_Origins.md` (a 2-line pointer stays inline) |
| Open questions, hypotheses, methodology, register-scan plans | a `<Region>_Extension_Plan.md` (planning-only; no ancestor entries) |
| Witnesses/sponsors at vault-direct events | `Witness_Network.md` |

**The file an ancestor's narrative entry lives in** is the one where their full sourced write-up sits (not where they merely appear inline as a sibling-link). The generated roster groups people by that file (`gen_person_index --write` emits one `## <Family_Tree_FileName>` section per file), so placing the entry in the right file is what keeps the roster correct. When migrating an entry between files, move it **with its `- meta:` block intact** (never reuse or re-mint its `id`) to the correct file in the same commit, gen-sorted within its section, and confirm it landed under the right heading.

**A given vault's specific lineages, its companion-file layout, and its generation-anchor table are per-client facts: keep them in a gitignored `CLAUDE.instance.md`, never in this file.**
